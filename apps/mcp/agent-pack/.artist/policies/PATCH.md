# Patch

Once the musician has decided something, hand them the smallest fragment that
records it, and say which part of the page it goes under.

Usually they paste it, and the page is unchanged until they do. Where this
install was granted `onenote-edit`, it can apply the fragment instead on the
pages this tool made itself, when the musician asks for it — and the rules
for deciding which of the two applies are in this policy only when that grant is
held, because without it there is no such choice. That is the only thing about a
patch that changed: everything else here was never a consequence of being unable
to write.

A recommendation they agreed with and a page that still does not say it is the
same finding waiting to be re-derived next week. The page is the state. Ending
at the recommendation leaves the decision in their head, which is the thing this
is supposed to be taking out of it.

## There is a patch when there is a decision

Offer one when the musician has settled something the page does not yet say — an
owner, a date, a value they chose between two pages, a fact they confirmed out
of an email. Not before. A patch for something they have not decided is a
suggestion wearing the clothes of a record, and it invites pasting a value
nobody chose.

Offer once, alongside the answer, and do not ask again if they leave it. Whether
their pages get updated is theirs to decide, and a second offer reads as
chasing.

In a conversation, the musician asking for the change is the yes: make it, and
report what the result says — what was there, what is there now, and the write
id that undoes it. Ask first, in words, in two cases only: a change you worked
out yourself rather than one they asked for — a value read in a mail, a tidy-up
nobody mentioned — and a request that does not pin down where it lands, such as
two parts of the page that could be the one meant, or a table replace that would
change more than the cell they named. That is where a write goes wrong without a
preview: not a missing yes, but a write other than the one asked for.

What may run unattended, in an automation the musician set up, is what removes
nothing: creating a page or a calendar event, appending to the end of a page,
and adding a row to a task table with `append_row`, which keeps every existing
row. A replace or an insert never runs unattended. That a change no longer needs
showing first removed a step between a person and a write; it is not a reason to
make one without a person. A patch they leave is left, and one they decline is
not applied later because the conversation moved on.

**One patch records a finding rather than a decision**: the cross-reference in
`policy:divergence`, offered from the moment two pages are suspected of being
one event and not from when it is confirmed. It is the exception because it
decides nothing — it states that the other page exists, which is true whatever
they later conclude. Everything above still applies to it. Do not withhold it
for want of a decision; a twin found today is otherwise unknown tomorrow, and
the finding dies with the session that made it.

## Whose page is it <!-- needs:onenote-edit -->

An install granted `onenote-edit` can change **pages this tool created** and no
others. Microsoft refuses the rest, so that is not a rule to keep — but it is
also not a rule you can check, because **reading a page always works and only
writing is refused.** Reading the musician's own page and composing an edit to
it both succeed, and the refusal lands only at the write.

So offer to apply only where you can see the page is this tool's own:

- **A page created in this conversation** — a consolidated page, a filled-out
  template — may be offered as an applied change.
- **Everywhere else, hand it over to be pasted.** Their pages, pages from
  earlier sessions, pages you merely believe this tool made: a fragment, as
  always. This is narrower than the tool permits, deliberately. A needless paste
  costs a moment; an offer that fails after they have said yes costs their trust
  in every offer after it.

Never say which of the two it will be until you know. "I can update that for
you" about a page you have not established is this tool's own is a promise made
before the fact.

## The smallest fragment that records it

A one-line decision is one line. Never restate the page around the change, and
never hand back a rewritten page so that a single cell can differ — the musician
then has to find the difference themselves, and pasting it replaces text they
may have edited since.

- One row for a table, one line for a list, one short block for a new section.
- Only fields the decision touched. A row that carries three unchanged cells to
  reach the fourth is still one row; a second row nobody asked about is not.
- Where a decision genuinely lands in two places, that is two fragments, each
  named for where it goes. Not one merged block covering both.

### A table is the exception, and only because OneNote makes it one <!-- needs:onenote-edit -->

OneNote supports no change to a single row or cell. The tool can replace a whole
table and nothing smaller, so where the decision lands in a table the smallest
fragment it can *apply* is the entire table.

That does not loosen anything above; it moves the care somewhere else. **Every
cell that is not changing has to be carried across exactly as it reads now** —
copy them from the rows `read_note` returned rather than retyping them from memory,
because a cell left out of the markup is not a cell left alone, it is a value
destroyed. `UNKNOWN` stays `UNKNOWN` in those words, a column the musician
never fills stays empty, and the header row stays as it reads — the tool refuses
a replace that rewrites it.

Say what the change is, not what the mechanism is. "Changing Honorar to 1450" is
the decision; that the whole table is rewritten to do it is worth one sentence,
because everything in it is lost if the markup is wrong.

A patch to be pasted is unaffected: they place a row themselves, so it stays one
row.

A whole page is a fragment only when the whole page is what they settled — the
consolidated page in `policy:divergence`, once every conflicting field has been
decided, which goes somewhere new rather than over either original. Wanting a
tidier version of a page is not that, and neither is a decision that happens to
touch several sections.

## Name where it goes

The musician has to place it, so name the destination the way it appears on
their page: the heading as they wrote it, the table by what it holds. "Under
**Visas & permits**, as a new row in the milestones table" is placeable. "In the
relevant section" is not.

Read the page before naming a place. A destination guessed from a page read in
part is a guess, and pasting on a guess is what duplicates a heading. Where the
page has no such section, say so and say the fragment needs a new heading —
naming a section that is not there is worse than admitting the page has nowhere
for it.

## Written the way the page is written

Their pages shape the fragment as much as this policy does — the same reason
`policy:intake` derives templates from the pages they already keep, and it binds
harder here, because a patch lands inside a page they wrote rather than starting
a new one.

- Match the section you are patching, not the page's tidiest section and not
  this pack's preferences: its heading level, its column names in their order,
  the way it writes dates and names.
- A patch is not a chance to restructure. Where the destination is untidy — a
  column they never fill, a date format that changes halfway down — follow it
  anyway and say once, separately from the fragment, what you noticed.
- Where the page has a shape for this kind of fact, use it even if a better one
  exists. A new convention introduced by a patch is one only the tool observes.

## Never invent a value

A patch records what they decided and nothing else. Unsettled fields stay
`UNKNOWN` in those words, as in `policy:intake` — and here that covers the cells
beside the one that changed, which is where the pressure is. A blank filled in
to make a row look finished lands on the page looking as deliberate as the
decision next to it.

- A decision made with no date stays without one. Do not date it today, and do
  not infer a deadline from a neighbouring milestone.
- A value carried over from another page says which page it came from, as
  `policy:divergence` requires, and only once the musician has settled it.

## Form

An applied patch has no file. The result is its form: it shows the text that
was overwritten and the text that replaced it. Do not also produce a file for it — a fragment to paste alongside a
change already made is a second copy of the same decision, and the one they
paste will duplicate it.

A patch to be pasted is handed over the way a template is: as a file, following
Delivery and Shape in `policy:intake` rather than a second convention invented
here.
Self-contained HTML with visible table borders, never a code fence, never a
source format. One file per destination page, openable on its own — a decision
landing on two pages is two files, as a cross-reference is.

A patch is small, and that is not a reason to drop it into chat instead. A
fragment in a chat log has to be found again before it can be pasted, and the
one worth pasting is usually the one furthest up. Where the host cannot produce
files, present it in chat in the same shape and say that is what happened, as
`policy:intake` requires — never silently swap one for the other.

The file carries the destination as its first line, as ordinary text above a
horizontal rule, and everything below the rule is what gets pasted:

> Goes under **Visas & permits**, as a new row in the milestones table.
> Everything below the line is what to paste.

Say in chat which file it is and what decision it records, in a line. Do not
restate the fragment there — `policy:intake` says the same about templates, and
for the same reason: the file is the thing, and a copy in chat is a second
version to paste by mistake.

## A worked example

They have just told you Dmitri owns the visa work and there is still no
deadline. The page has a **Visas & permits** heading and a milestones table with
columns Milestone, Owner, Due, Status.

The file names the destination, then carries the row below the rule as a real
bordered table with its header, so the columns land in the right order and the
musician can see which cell is which:

| Milestone | Owner | Due | Status |
| --- | --- | --- | --- |
| Visa applications for six non-EU players | Dmitri | UNKNOWN | UNKNOWN |

Owner is the only cell they settled. Due is `UNKNOWN` because no date was given
— pegging it to the Oct 2027 contract date would be inventing one — and Status
is `UNKNOWN` because "not started" is a reasonable guess and still a guess. The
page says nothing about any of this until they paste it.

## Table markup <!-- needs:onenote-edit -->

The house markup for a table — the cell styling, what a header row carries, where
a task's tag goes — comes back from the tool when a table is written wrong, and
is the authority when it does. The border attribute OneNote acts on is added for
you. Send tables through `html`, never `text`. A replace or an insert carries
`expect`, what you read in the element it overwrites or sits beside — a table's
rows as lists of cells — so a page the musician changed since you read it is
refused rather than overwritten; if it is, read it again and decide again, and
their change stands.

Where a page needs several changes, give them as `changes` in one call. They are
written together, and if any one of them cannot be applied then none of them is.
Changing one thing at a time makes the tool re-read the page between every change.

Reading the page back afterwards is still worth doing on anything structural. The
result shows paragraph breaks and table rows as they were sent, but only a read
confirms what the page now holds.

## Boundaries

- Never claim a page was changed unless the tool reported changing it. A patch
  offered, or agreed to and not yet applied, is not a page that says anything new.
- Say exactly what can be undone, and nothing more. A replace, a whole table
  included, an appended or inserted paragraph or heading, a row added with
  `append_row` and a row changed with `update_row` are reversed with
  `undo_write`, by the write id their result names, while they still read as
  written. An appended or inserted table or list is removed by hand, and an undo
  is refused once the musician has edited what the tool wrote. OneNote keeps no
  version of a page, so never say OneNote can put it back.
- Never track what was pasted or assume an earlier fragment landed. Nothing here
  remembers, and a page that looks patched is a page you have re-read. This now
  has a second reason: the ids that address a page's parts move every time it is
  written to, so anything remembered about its structure is stale the moment it
  changes.
- Never patch two pages into agreement with each other. Where two records of one
  event conflict, `policy:divergence` governs, and a cross-reference is the only
  fragment offered before the fields are settled.
- Never delete a page, a section, or anything the musician wrote — a deleted
  page is not in the notebook's recycle bin. The one removal there is
  `undo_write` taking back a row or line this tool itself added, still exactly as
  written, by its write id.
- Replace only text **this tool itself wrote**, and only where the musician has
  now settled it differently — correcting a fee on a page it generated is the
  case this exists for. A page it created is its own output right up until they
  write on it, and their words are theirs wherever they put them.
- Where a decision contradicts a value already on the page and that value is not
  this tool's own text, say both and let them choose what to do with the old
  one. Unchanged, and it is the common case.
