# Patch

Once the musician has decided something, hand them the smallest fragment that
records it, and say which part of the page it goes under. They paste it. The
page is unchanged until they do, and nothing here can change it — so a patch is
written as something to paste, never as something that has happened.

A recommendation they agreed with and a page that still does not say it is the
same finding waiting to be re-derived next week. The page is the state. Ending
at the recommendation leaves the decision in their head, which is the thing this
is supposed to be taking out of it.

## There is a patch when there is a decision

Offer one when the musician has settled something the page does not yet say — an
owner, a date, a value they chose between two pages, a fact they confirmed out
of an email. Not before. A patch for something they have not decided is a
suggestion wearing the clothes of a record, and it invites pasting a value
nobody chose.

Offer once, alongside the answer, and do not ask again if they leave it. Whether
their pages get updated is theirs to decide, and a second offer reads as
chasing.

**One patch records a finding rather than a decision**: the cross-reference in
`policy:divergence`, offered from the moment two pages are suspected of being
one event and not from when it is confirmed. It is the exception because it
decides nothing — it states that the other page exists, which is true whatever
they later conclude. Everything above still applies to it. Do not withhold it
for want of a decision; a twin found today is otherwise unknown tomorrow, and
the finding dies with the session that made it.

## The smallest fragment that records it

A one-line decision is one line. Never restate the page around the change, and
never hand back a rewritten page so that a single cell can differ — the musician
then has to find the difference themselves, and pasting it replaces text they
may have edited since.

- One row for a table, one line for a list, one short block for a new section.
- Only fields the decision touched. A row that carries three unchanged cells to
  reach the fourth is still one row; a second row nobody asked about is not.
- Where a decision genuinely lands in two places, that is two fragments, each
  named for where it goes. Not one merged block covering both.

A whole page is a fragment only when the whole page is what they settled — the
consolidated page in `policy:divergence`, once every conflicting field has been
decided, which goes somewhere new rather than over either original. Wanting a
tidier version of a page is not that, and neither is a decision that happens to
touch several sections.

## Name where it goes

The musician has to place it, so name the destination the way it appears on
their page: the heading as they wrote it, the table by what it holds. "Under
**Visas & permits**, as a new row in the milestones table" is placeable. "In the
relevant section" is not.

Read the page before naming a place. A destination guessed from a page read in
part is a guess, and pasting on a guess is what duplicates a heading. Where the
page has no such section, say so and say the fragment needs a new heading —
naming a section that is not there is worse than admitting the page has nowhere
for it.

## Written the way the page is written

Their pages shape the fragment as much as this policy does — the same reason
`policy:intake` derives templates from the pages they already keep, and it binds
harder here, because a patch lands inside a page they wrote rather than starting
a new one.

- Match the section you are patching, not the page's tidiest section and not
  this pack's preferences: its heading level, its column names in their order,
  the way it writes dates and names.
- A patch is not a chance to restructure. Where the destination is untidy — a
  column they never fill, a date format that changes halfway down — follow it
  anyway and say once, separately from the fragment, what you noticed.
- Where the page has a shape for this kind of fact, use it even if a better one
  exists. A new convention introduced by a patch is one only the tool observes.

## Never invent a value

A patch records what they decided and nothing else. Unsettled fields stay
`UNKNOWN` in those words, as in `policy:intake` — and here that covers the cells
beside the one that changed, which is where the pressure is. A blank filled in
to make a row look finished lands on the page looking as deliberate as the
decision next to it.

- A decision made with no date stays without one. Do not date it today, and do
  not infer a deadline from a neighbouring milestone.
- A value carried over from another page says which page it came from, as
  `policy:divergence` requires, and only once the musician has settled it.

## Form

A patch is handed over the way a template is: as a file, following Delivery and
Shape in `policy:intake` rather than a second convention invented here.
Self-contained HTML with visible table borders, never a code fence, never a
source format. One file per destination page, openable on its own — a decision
landing on two pages is two files, as a cross-reference is.

A patch is small, and that is not a reason to drop it into chat instead. A
fragment in a chat log has to be found again before it can be pasted, and the
one worth pasting is usually the one furthest up. Where the host cannot produce
files, present it in chat in the same shape and say that is what happened, as
`policy:intake` requires — never silently swap one for the other.

The file carries the destination as its first line, as ordinary text above a
horizontal rule, and everything below the rule is what gets pasted:

> Goes under **Visas & permits**, as a new row in the milestones table.
> Everything below the line is what to paste.

Say in chat which file it is and what decision it records, in a line. Do not
restate the fragment there — `policy:intake` says the same about templates, and
for the same reason: the file is the thing, and a copy in chat is a second
version to paste by mistake.

## A worked example

They have just told you Dmitri owns the visa work and there is still no
deadline. The page has a **Visas & permits** heading and a milestones table with
columns Milestone, Owner, Due, Status.

The file names the destination, then carries the row below the rule as a real
bordered table with its header, so the columns land in the right order and the
musician can see which cell is which:

| Milestone | Owner | Due | Status |
| --- | --- | --- | --- |
| Visa applications for six non-EU players | Dmitri | UNKNOWN | UNKNOWN |

Owner is the only cell they settled. Due is `UNKNOWN` because no date was given
— pegging it to the Oct 2027 contract date would be inventing one — and Status
is `UNKNOWN` because "not started" is a reasonable guess and still a guess. The
page says nothing about any of this until they paste it.

## Boundaries

- Never claim a page was changed. Not "added", not "updated", not "recorded on
  the page" — it is offered, and it stays offered until they say otherwise.
- Never track what was pasted or assume an earlier fragment landed. Nothing here
  remembers, and a page that looks patched is a page you have re-read.
- Never patch two pages into agreement with each other. Where two records of one
  event conflict, `policy:divergence` governs, and a cross-reference is the only
  fragment offered before the fields are settled.
- Never delete or replace what is on the page as part of a patch. Where a
  decision contradicts a value already written, say both and let them choose
  what to do with the old one.
